== Scope

This guide describes how to build, test, package, and release `capella2sysmlv2` from source.

For installation and command-line usage, see link:../README.adoc[the user documentation].
For implemented capabilities and planned work, see link:project-status.adoc[Project Status and Roadmap].

== Development Requirements

The development environment requires:

* JDK 21;
* Maven 3.9 or later;
* Git;
* network access to Maven Central, Eclipse p2 repositories, and GitHub Packages;
* Asciidoctor when rendering documentation locally.

Check the active toolchain before building:

[source,bash]
----
java -version
mvn -version
----

Both commands must report the intended JDK 21 installation.

== GitHub Packages

The build consumes artifacts from the SysON, Sirius, Sirius EMF JSON, Arcadia, and Capella for SysON GitHub Packages repositories.
GitHub Packages may require authentication even when the corresponding source repositories are public.

Create a GitHub personal access token (classic) with the `read:packages` permission, and grant its account read access to the Capella for SysON package if required. Then expose its account and token to Maven:

[source,bash]
----
export MAVEN_GITHUB_USERNAME=<github-account>
export MAVEN_GITHUB_TOKEN=<token-with-read-packages>
----

The committed `.github/maven-settings.xml` file maps these environment variables to all required repository identifiers without storing credentials.
Use it with:

[source,bash]
----
mvn --settings .github/maven-settings.xml clean verify
----

If equivalent servers are already configured in `~/.m2/settings.xml`, the explicit `--settings` argument can be omitted.

Never commit a token or a generated settings file containing a token.

The Eclipse application build downloads `arcadia.json` from the `main` branch of the Capella for SysON repository into the application bundle.

== Repository Structure

=== Regular Maven Modules

`capella-loader`::
Contains the model loading contracts and secure Capella project archive extraction.

`capella2sysmlv2-transformer`::
Contains the dependency-driven transformation engine, the concrete transformation context, diagnostics, traceability, target structure creation, and semantic mappings.

`cli`::
Contains the Java command-line entry point and the runtime-independent transformation service contract.

`integration-tests`::
Contains functional and integration scenarios.

`test-support`::
Provides reusable test resources and golden-file assertions.

=== Equinox and Tycho Modules

`eclipse/target-platform-<version>`::
Defines the selected Capella metamodel, EMF, Equinox, and Kitalpha target platform.

`eclipse/plugins/org.eclipse.capella.sysmlv2.bridge.mappings`::
Contains typed Capella mapper implementations and the curated alignment backlog.

`eclipse/plugins/org.eclipse.capella.sysmlv2.bridge.application`::
Implements the Equinox application, typed Capella resource loading, transformation orchestration, bundled Arcadia library loading, and intermediate XMI persistence.

`eclipse/tests/org.eclipse.capella.sysmlv2.bridge.mappings.tests`::
Tests typed mappings against small EMF models.

`eclipse/features`::
Defines the standalone headless product feature.

`eclipse/product`::
Materializes and archives the Linux and Windows standalone products.

`eclipse/official-product-it`::
Runs the IFE integration scenario against the packaged standalone product.

== Architecture

The production pipeline is:

[source,text]
----
Input zip archive
        |
        v
Secure project extraction
        |
        v
Capella metamodel package registration
        |
        v
Direct .capella semantic model loading
        |
        v
Typed mapper registry resolution
        |
        v
Dependency-driven TransformationEngine
        | prerequisite construction and registration
        | feature mapping
        |
        v
SysON SysML v2 model using Arcadia concepts
        |
        v
Intermediate XMI persistence and reload validation
----

The transformation layer does not initialize Equinox, load projects, or serialize textual SysML.
The engine resolves the definitions required by the generated model structure from the shared `ResourceSet`.
It attaches the generated root to that same `ResourceSet` before creating targets, allowing SysON services to discover Arcadia concepts through `SysONEContentAdapter`.

`MapperRegistry` resolves the first compatible mapper in registration order and rejects duplicate source classes.
The registry uses the mapper's typed Java source class.

=== Dependency-driven construction

`TransformationEngine.transform(root, rootName)` traverses the root and its descendants; `transformAll(sources, rootName)` accepts a `Collection<? extends EObject>` of explicit sources. Both methods invoke mappers only for sources supported by the registry. The `rootName` string names the generated model root.

Sources are indexed by object identity and duplicates are ignored. Independent sources retain encounter order. Each mapper declares its creation prerequisites through `getCreationDependencies(source)`, using read-only source inspection without traceability. Only prerequisites in the supplied scope can be constructed.

The engine recursively resolves dependencies with `CONSTRUCTING`, `READY`, and `FAILED` states. It creates and registers each successful target once. Missing, unsupported, excluded, failed, or out-of-scope prerequisites prevent dependent creation and produce a diagnostic identifying the prerequisite. Cycles report their active source path and fail the affected chain while unrelated sources continue. Discovery and creation exceptions, and null results, exclude the source without retries or placeholders.

Functions and components select the nearest compatible source ancestor within their perspective, traversing unmapped packages. Architecture roots reuse the targets provided by `ArcadiaModelStructureBuilder` without a parent dependency. Other elements pass the selected mapped ancestor to their existing creation service; only absence of a compatible source ancestor permits the existing perspective fallback. Ports require their mapped owners and set direction during creation. Creation services own containment: their results are never relocated to reproduce the Capella hierarchy.

After every construction attempt finishes, successful targets receive their feature mappings once, in construction-completion order. Names, descriptions, allocations, and realizations remain feature mappings. Cross-reference feature mappings do not contribute construction dependencies. Feature failures produce diagnostics while subsequent mappings continue.

The public services are concrete single implementations: `TransformationContext`, `Traceability`, `DiagnosticsCollector`, and `MapperRegistry`. `ElementMapper` exposes `getCreationDependencies`, `createAndRegister`, and `mapFeatures`; `FeatureMapping` stores coverage metadata and a context-aware action. Catalog registration requires no priorities. Coverage-report containment fields still describe the Capella metamodel.
The transformation context contains the model structure, identity-based traceability, diagnostics, and exclusion state. It does not contain transformation options or a deferred reference resolver.
The Equinox application registers the installed Capella packages, maps `platform:/resource` URIs to the extracted project, and loads the `.capella` resource directly into a Capella semantic editing domain with a Sirius cross-reference adapter. It requires a typed Capella `Project` root and does not create an Eclipse workspace, load an `.aird` resource, or open a Sirius session.
Standalone loading removes TED's session-aware `DataNotifier` immediately after editing-domain creation. The notifier is only useful with a Sirius session and otherwise activates the full Sirius bundle during model notifications; the `SiriusCrossReferenceAdapter` remains installed for direct and inverse derived references.

== Build and Test

=== Regular Build

The required repository build is:

[source,bash]
----
mvn clean verify
----

With explicit GitHub Packages settings:

[source,bash]
----
mvn --settings .github/maven-settings.xml clean verify
----

This build runs the regular unit, functional, and integration tests without starting Capella.

=== Standalone Products

Choose one product profile per build. The release workflow runs `capella-product-7.1.0` and `capella-product-7.0.1` separately.

To package the Capella 7.0.1 products for Linux and Windows, run:

[source,bash]
----
mvn --settings .github/maven-settings.xml \
  -Pcapella-product-7.0.1 \
  -DskipTests \
  clean package
----

The materialized products are created under:

[source,text]
----
eclipse/product/org.eclipse.capella.sysmlv2.bridge.product.7.0.1/
  target/products/org.eclipse.capella.sysmlv2.bridge.product.7.0.1/linux/gtk/x86_64/
  target/products/org.eclipse.capella.sysmlv2.bridge.product.7.0.1/win32/win32/x86_64/
----

The distributable archives are:

[source,text]
----
eclipse/product/org.eclipse.capella.sysmlv2.bridge.product.7.0.1/target/products/
  org.eclipse.capella.sysmlv2.bridge.product.7.0.1-linux.gtk.x86_64.tar.gz
  org.eclipse.capella.sysmlv2.bridge.product.7.0.1-win32.win32.x86_64.zip
----

=== Product Integration Test

Run the complete build and standalone IFE product integration test with:

[source,bash]
----
mvn --settings .github/maven-settings.xml \
  -Pcapella-product-7.0.1 \
  clean verify
----

The materialized standalone product is launched without `DISPLAY`. The test gives it an archive containing only `.project` and `.capella` files, then checks the typed Capella source model, transformation summary, generated XMI model, and Arcadia references.

=== Manual Linux Test

After building the product, download the sample:

[source,bash]
----
curl -L \
  "https://www.eclipse.org/downloads/download.php?file=/capella/samples/7.0.1/InFlightEntertainmentSystem.zip&r=1" \
  -o /tmp/InFlightEntertainmentSystem.zip
----

Run the materialized Linux product:

[source,bash]
----
env -u DISPLAY \
  eclipse/product/org.eclipse.capella.sysmlv2.bridge.product.7.0.1/target/products/\
org.eclipse.capella.sysmlv2.bridge.product.7.0.1/linux/gtk/x86_64/capella2sysmlv2 \
  -vm "$JAVA_HOME/bin/java" \
  /tmp/InFlightEntertainmentSystem.zip \
  /tmp/capella2sysmlv2-output
----

Check for `Errors: 0` and compare the CLI coverage summary with `output/.capella2sysmlv2/transformation-instance-report.md`.

=== Registering a Mapper

Implement the typed mapper in the mappings bundle, declare its feature mappings, add focused tests, and register it in `CapellaMapperCatalog.createMappers()`. The catalog also records assessed candidates such as `Mission` for future work.

=== Semantic Mapping Coverage Reports

Every successful transformation writes two Markdown reports under `OUTPUT_DIRECTORY/.capella2sysmlv2/`.

* `transformation-instance-report.md` records the input model coverage, diagnostics and Arcadia library usage for the run. The CLI prints the same input model coverage and the error count.
* `transformation-meta-report.md` describes Capella metaclass and feature mappings, alignments and the Arcadia library concept assessment. Each library concept is classified as implemented, a backlog candidate, explicitly not mapped, or unassessed.

Mapper declarations that reference an unknown Arcadia concept or feature cause report generation to fail.

== Release Automation

The `.github/workflows/release.yml` workflow qualifies pull requests, pushes to `main`, manual runs, and release tags.
Release tags must follow strict `vMAJOR.MINOR.PATCH` syntax.

=== Repository Secrets

Configure these Actions secrets in the GitHub repository:

`MAVEN_GITHUB_USERNAME`::
The GitHub account that owns the package access token.

`MAVEN_GITHUB_TOKEN`::
A token with `read:packages` access to the required SysON, Sirius, Arcadia, and Capella for SysON packages. GitHub Packages requires a classic personal access token for Maven authentication.

The workflow uses the built-in `GITHUB_TOKEN` with `contents: write` only when publishing the release.

=== Release Sequence

The workflow performs the following operations:

. validates semantic-version tags and their ancestry from `main`;
. executes the complete Maven, Tycho, and standalone product build with Java 21;
. materializes the Linux and Windows products;
. renames the archives to stable public asset names;
. runs the IFE scenario from the Capella 7.1.0 Linux archive without `DISPLAY`;
. runs the IFE scenario from the Capella 7.1.0 Windows archive on a Windows runner;
. verifies input model coverage and the error count, Arcadia references, and Java 21 runtime;
. uploads diagnostic logs after failures;
. creates the GitHub Release for tags only and only after every preceding job succeeds.

The workflow runs both qualification commands with Java 21:

[source,bash]
----
mvn --settings .github/maven-settings.xml \
  -Pcapella-product-7.0.1 \
  clean verify

mvn --settings .github/maven-settings.xml \
  -Pcapella-product-7.1.0 \
  clean verify
----

The standalone acceptance test demonstrates that semantic model loading and transformation use Capella's semantic editing domain and derived references without requiring a display server, Eclipse workspace, `.aird` file, or Sirius session.

Create a release from an up-to-date `main` branch with:

[source,bash]
----
git switch main
git pull --ff-only
git tag -a v0.1.0 -m "Release v0.1.0"
git push origin v0.1.0
----

The release publishes these stable assets:

* `capella2sysmlv2-Capella.7.0.1-linux-x86_64.tar.gz`
* `capella2sysmlv2-Capella.7.0.1-windows-x86_64.zip`
* `capella2sysmlv2-Capella.7.1.0-linux-x86_64.tar.gz`
* `capella2sysmlv2-Capella.7.1.0-windows-x86_64.zip`

The user documentation links to the corresponding `/releases/latest/download/` URLs.

Do not move or recreate a published release tag.

== Contribution Rules

New functionality follows a test-driven sequence:

. add or update a minimal source model or metamodel;
. add focused assertions;
. execute the failing test;
. implement the smallest correct change;
. verify target structure, traceability, diagnostics, and references;
. run `mvn clean verify`.

Contributions must not:

* introduce Capella UI, Eclipse UI, or Sirius session behavior into the transformation flow;
* depend on the SysML v2 Reference Implementation;
* implement a private textual SysML serializer;
* hardcode local paths;
* let mappers load the Arcadia library directly;
* place transformation semantics in the engine orchestration, loader, or CLI;
* keep mutable execution state in mapper instances.

Contributions must:

* follow the coding guidelines available in releng/resources
